# Synetra 全功能端到端测试方案

> 版本 v1.0 ｜ 2026-11-10 ｜ 适用基线：当前 `main` 工作区（OpenSpec 无活跃 change，基线 `dataflow-v2`）
> 目标：以浏览器自动化**模拟真人操作**，对平台全部功能面做一次系统验收，并产出可复核的测试文档。

---

## 1. 测试目标与范围

### 1.1 目标

1. 验证 11 个业务页面 + 3 个模态（运行详情 / 流水线画布 / 生成记录）在真实浏览器中的**可用性、正确性、交互完整性**。
2. 验证跨模块的**端到端业务链路**：连接 → 查询 → 任务编排 → 运行 → 监控 → 血缘。
3. 验证 **RBAC 三角色差异**（admin / developer / readonly）与关键错误路径的降级表现。
4. 沉淀一份可重复执行的自动化资产 + 一份人可读的测试报告（含截图证据、缺陷清单）。

### 1.2 范围内

| 能力域 | 覆盖方式 |
| --- | --- |
| 认证与会话、角色可见性 | UI + API |
| 总览、连接管理、只读查询/接口调试 | UI |
| 项目与任务编排、字段映射、数据预览、可视化流水线画布 | UI |
| AI ETL 任务（对话式生成） | UI（无 Key 场景 + 记录页） |
| 定时任务（启停、cron 校验） | UI |
| 监控告警（运行历史、日志、指标、对账、告警事件） | UI |
| 元数据与血缘 | UI |
| 主数据管理（实体定义） | UI |
| 权限与凭据（用户 CRUD、改密、保护规则） | UI |
| AI 管理（模型配置、技能包） | UI（admin） |
| 有 UI 入口以外的后端端点（脚本/触发/凭据/MDM 记录） | API 层补充校验 |

### 1.3 范围外（明确不测）

| 项 | 原因 |
| --- | --- |
| LLM 真实生成质量 | 无 DeepSeek API Key；只验证"未配置 → 503 降级"与"配置保存/吊销"链路 |
| SMTP 真实发信 | 无 SMTP 凭据；只验证告警降级为日志、事件表空态 |
| 主机资源真实数值 | Windows 无 `/proc`，`GET /api/monitor/system` 预期 500，只断言前端降级文案 |
| 部署脚本 `deploy/install.sh`、systemd | 属运维验收，另立方案 |
| 性能/压力测试 | 另立方案（本方案只做分页与大结果集的基本健壮性） |
| 移动端/响应式 | 产品定位桌面工作台 |

## 3. 数据与隔离策略

```
┌──────────────────────────────────────────────────────────────┐
│  测试环境（每次全量执行前重建，执行后可一键 DROP）            │
├──────────────────────────────────────────────────────────────┤
│  元数据库   synetra_e2e        ← SYNETRA_METADATA_DB_DSN 指向  │
│  数据源库   synetra_e2e_src    ← 建 e2e_orders(25行) 等样例表  │
│  目标库     synetra_e2e_dst    ← 验证写入 / upsert / 幂等      │
│  运行时目录 services/backend/data-e2e（独立 SYNETRA_DATA_DIR）│
│  日志/报告  reports/e2e/<run_id>/                             │
└──────────────────────────────────────────────────────────────┘
        ▲ 绝不改写用户现有的 synetra / aitest 库
```

- 命名规范：项目 `E2E-<模块>`、连接 `e2e-<类型>-<序号>`、任务 `e2e-task-<n>`、用户 `e2e-<role>-<n>`。
- 数据准备走 **API fixture**（`POST /api/projects|connections|tasks|users|mdm/models`），UI 只负责"用户视角的操作"与断言，避免用 UI 造 60 次数据导致噪声失败。
- 清理：按 `E2E-` 前缀回收（API `DELETE`），环境级对象（库/目录）在 teardown 整体删除。
- **破坏性用例（删除连接/任务/项目/用户）排在所属模块末尾**，只删自建数据。

## 4. 测试分层

```
                 ┌───────────────────────────────┐
   L4 回归       │  pytest（37 文件）+ ruff       │  既有资产，验证无回归
                 └───────────────────────────────┘
                 ┌───────────────────────────────┐
   L3 业务链路   │  连接→查询→任务→运行→监控→血缘 │  跨页面 5 条主链路
                 └───────────────────────────────┘
                 ┌───────────────────────────────┐
   L2 功能用例   │  11 页面逐页功能矩阵（~75 例） │  本方案主体
                 └───────────────────────────────┘
                 ┌───────────────────────────────┐
   L1 UI 冒烟    │  登录 / 12 项导航可点 / 无白屏 │  分钟级，先跑
                 └───────────────────────────────┘
                 ┌───────────────────────────────┐

                 └───────────────────────────────┘
```

**执行顺序**：L0 → L1 → L2（按模块）→ L3 → L4；任一 L0/L1 失败即中止并出阻塞报告。

## 5. 自动化实现方案

### 5.1 选型

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **Playwright `@playwright/test`（chrome channel，headed）** | 可重复、可回归、内置 trace/video、自动等待、并行、HTML 报告 | 首次需装浏览器依赖 | **主方案** |
| agent-browser CLI（探索式） | 贴近"人工点"，适合发现脚本没覆盖的问题 | 不可回归、证据零散 | 辅：画布拖拽等复杂交互做探索补充 |

### 5.2 工程结构（新建，不改动现有源码）

```
services/frontend/e2e/
├── playwright.config.js      # 双 webServer（backend:8000 + vite:5173），baseURL 5173
├── fixtures/
│   ├── session.js            # 注入 localStorage["synetra.session"] 复用登录态
│   ├── seed.js               # API 造数 / 清理（E2E- 前缀）
│   └── selectors.js          # 统一选择器常量（中文文本 / placeholder / title）
├── specs/
│   ├── 01-auth.spec.js  02-overview.spec.js  03-connections.spec.js
│   ├── 04-query.spec.js 05-projects-tasks.spec.js 06-pipeline-canvas.spec.js
│   ├── 07-ai-task.spec.js 08-schedules.spec.js 09-monitor.spec.js
│   ├── 10-lineage.spec.js 11-mdm.spec.js 12-security.spec.js 13-llm-admin.spec.js
│   ├── 14-e2e-flows.spec.js 15-negative.spec.js
└── utils/report.js           # JSON 结果 → doc/test-report.md 生成
```

### 5.3 三个必须适配的实现事实（探查结论）

1. **前端已有 hash 路由**（变更 `fix-test-report-defects` 起）：切页写入 `#/<key>`，刷新保持、深链可直达。→ 仍封装 `gotoPage('连接管理')` 走侧边栏点击，深链场景用 `page.goto('/#/monitor')` 单独验证。
2. **登录态是 localStorage 里 `{username, role, token, exp}` + 请求头 `Authorization: Bearer <token>`**，服务端验签。→ `actAs()` 先调 `/api/auth/login` 取真实票据再写入 localStorage，实现"角色切换"；直接调接口用 `authHeaders()`；同时保留 1 条真实走登录表单的用例。
3. **0 个 `data-testid`**：选择器策略按稳定性排序 —— `#login-user` / `#login-pass`（已有 id） > `getByPlaceholder` > `getByRole('button', { name })` > `title` 属性 > 中文文本。⚠️ 若某控件确无稳定选择器，**优先在 `selectors.js` 内做作用域限定（Modal 内、表格行内）**，不修改产品代码。

### 5.4 证据与报告

- 每个用例：`beforeEach` 截图 → 关键步骤截图 → 失败时保留 `trace.zip` + `video.webm` + 控制台错误。
- `screenshot: 'only-on-failure'` + 关键断言点手动 `page.screenshot()`，产物落 `reports/e2e/<run_id>/<模块>/`。
- 结束后 `utils/report.js` 汇总为 `doc/test-report.md`：用例表（ID/结果/耗时/截图链接）+ 缺陷清单 + 环境指纹。

## 8. 判定标准

- **通过**：用例预期全部命中，无控制台 error、无 5xx（除"预期 500"的 MO-01）。
- **失败分级**：
  - **Blocker**：登录不可用、页面白屏、主链路断开 → 中止执行。
  - **Critical**：功能结果错误、数据写错。
  - **Major**：功能不可完成但可绕过、明确的权限缺口。
  - **Minor**：文案/空态/交互体验问题。
- **放行建议**：P0 全通过且无 Blocker/Critical 视为可发布；Major ≤ 3 且均有 issue 记录可灰度。
- **已知缺口**（第 6 节标 ⚠️）默认记 Major/Minor，不作为回归失败。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 无 `data-testid`，中文文本选择器易碎 | 用例不稳定 | `selectors.js` 集中管理 + 作用域限定；必要时允许一行 `data-testid`（需另开 change 提案） |
| 无 URL 路由 | 无法深链、刷新即回总览 | helper `gotoPage()` 统一点击导航；用例内不做刷新后状态断言（AUTH-04 除外） |
| `GET /api/monitor/system` 在 Windows 500 | 监控页资源卡失败 | 断言降级文案；如需真实指标，改用 Linux/容器环境 |
| 前端登录态无签名 | 无法测"会话过期" | 用"清 localStorage"模拟，明确记录为设计现状而非缺陷 |
| 流水线画布为 ReactFlow，节点拖拽 DOM 不稳定 | 画布用例易失败 | 主用"添加步骤下拉 + 配置表单 + 预览"，拖拽仅做探索式补充 |
| 定时触发依赖 20s 轮询 | 用例耗时不可控 | 用手动 `run` 验证执行通道；cron 只验配置持久化与下次时间计算 |
| `synetra` 存量库含真实配置 | 误删风险 | 强制隔离库 + `E2E-` 前缀 + 禁止对非自建对象执行删除 |
| LLM/SMTP 无凭据 | 相关功能无法正向验证 | 明确列为范围外，只验降级；报告注明"需人工补测" |

## 10. 执行决策（已确认，2026-11-10）

1. **载体**：Playwright 脚本（`services/frontend/e2e`），默认 headless，`E2E_HEADED=1` 可切有头观察。
2. **数据隔离**：独立元数据库 `synetra_e2e` + 独立 `data-e2e` 目录 + 自建 `synetra_e2e_src/dst` 样例库，不动既有数据。
3. **工程改动**：仅新增 `e2e/` 目录、`@playwright/test` devDependency 与 2 条 npm scripts（`test:e2e` / `test:e2e:headed`），**未改动任何 `src/` 业务代码**。
4. **报告**：中文，输出到 `doc/test-report.md`；执行结果见该文件。

> 实际执行结果与本方案的差异（用例数 106 而非 78、AUTH-06 归入 SEC-10、新增 TK-18/CN-09b/NEG-06 等回归型用例）以 [`doc/test-report.md`](./test-report.md) 为准。
