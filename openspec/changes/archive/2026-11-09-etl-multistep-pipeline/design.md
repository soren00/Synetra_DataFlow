# Design

## Context

动机见 `proposal.md`。设计受以下现状约束：

- `TaskConfig` 是任务配置的唯一来源，`fields[]` 为仅有的转换表达，且被 LLM 草稿、向导预填、血缘推导、dry-run 预览四处共同依赖（`app/models/task_config.py`、`app/llm/task_draft.py`、`app/metadata/catalog.py`、`app/transform.py`）。
- 执行链路分两段：配置渲染为脚本（`app/scripting/gen_config.py`）→ 子进程执行（`app/scripting/executor.py`），`etl_sdk` 约束脚本只能使用 `readers` / `writers`，绝不内联凭据。
- `etl_sdk` 的 `transforms.apply` 是空契约占位，说明「多步转换」在最初设计里就是预留位。
- 元数据（运行、日志、血缘）统一落 MySQL，本地磁盘只放脚本产物与 Vault 密钥。
- 前端为自研 macOS 设计语言组件，无第三方 UI 库；画布属于全新交互面。
- 现状执行器全量读入内存、逐行 INSERT；调度器误用 dry-run；水位从未注入。

## Goals / Non-Goals

**Goals:**

- 一个任务内可表达多次清洗与多源合并，配置可版本化、可 diff、可被 AI 生成与修订。
- 存量任务零迁移：旧 `fields` 配置加载即等价编译，行为与血缘不变。
- 执行正确性先于新能力：调度真写、水位真推进、大表不 OOM。
- 中间态可观测但不落业务库：步级指标入元数据，样本落本地。

**Non-Goals:**

- 不实现跨源等值关联（join / lookup），`value_map` 只做静态码表映射。
- 不实现单任务多目标扇出、错误行旁路、任务间依赖编排、断点续跑。
- 不追求 Kettle 级别的步骤数量与插件动态加载；步骤集合在编译期固定，注册表可扩展但需随版本发布。
- 不改变手写 Python 路径的安全模型与执行契约。

## Decisions

### D1. 图模型：节点 + 连线 DAG，而非线性步骤链

采用 `{"nodes": [...], "edges": [...]}` 的 DAG 表达，节点带 `type` 与 `config`。线性链无法表达多源 fan-in（合并节点需要多个入边），也无法表达同一源的多次分支处理。

- **备选**：线性 `steps[]` 列表（实现与 UI 都更简单）。否决原因：多源合并是本次明确需求，线性链只能靠「多个源节点 + 隐式拼接」表达，语义模糊且难以校验。
- **备选**：只做「任务链」（任务 A 写中间表 → 任务 B 读）。否决原因：污染数仓、血缘断裂、无法在单次运行内完成多趟清洗。

### D2. 执行模型：解释执行 + 薄脚本入口

`etl_sdk` 新增 pipeline 解释器，按拓扑序逐节点执行；保存时生成的脚本退化为 `run_pipeline(PIPELINE_SPEC)` 薄壳，仍走 current/versions、dry-run、人工确认链路。

理由：若继续把多步逻辑内联渲染进脚本，`gen_config.py` 将膨胀为一个弱类型 ETL 引擎，且 LLM 产出物不可控、无法做步级指标；解释器把「配置」变成唯一的执行事实源，同时保留既有版本化与 dry-run 能力。

- **备选**：继续内联渲染脚本。否决原因：不可维护、无法步级观测、每次新增步骤都要改代码生成器。
- **备选**：只做「配置解释执行」并废弃脚本产物。否决原因：破坏既有版本化、手写路径与 dry-run 契约，且与 37 条 `etl-authoring` 需求冲突。
- **兼容**：`readers` / `writers` 契约不变，historical 脚本与手写脚本继续执行，解释器只对含 `pipeline` 的配置生效。

### D3. 配置存储：`TaskConfig.pipeline` 内嵌 + `fields` 兼容编译

`fields` 保留在契约中，但降级为语法糖：读取时若 `pipeline` 缺失或为空，则按 `source → transform(fields) → target` 编译出三节点图；保存时同时写入编译结果与 `fields`（供旧客户端与旧血缘逻辑兜底）。

- **备选**：新增独立任务类型 / 新表存图。否决原因：任务列表、调度、监控、权限都以 `task_key` 为键，分裂实体要改一圈；且旧任务无法统一展示。
- **备选**：强制一次性迁移所有存量任务。否决原因：不可回滚、风险高，且无收益。

### D4. 多源合并：`union` 按列名对齐

合并节点取所有入边列的并集，按列名对齐，缺失列补空，同名类型冲突按统一提升规则（bool < int < float < decimal < str < text；timestamp 与 str 冲突取 str 并在节点上告警）。合并结果允许用户改列名与顺序。

- **备选**：按列位置对齐（Kettle 的 Union 也支持按位置）。否决原因：多源列序不一致时极易错位，且错误静默。
- **备选**：合并即落临时表再读。否决原因：见 Non-Goals 与写入策略。

### D5. 内存策略：分批流式 + 仅 blocking 步骤物化 + 超限溢出

源端按 `batch_size` 分批；行级步骤逐批处理不缓存全量；`sort` / `unique` / `aggregate` / `union` 标记为 blocking，物化量超过 `spill_threshold_mb` 时写本地 spill 文件（`data/spill/{run_id}/`）并继续。

- **备选**：全量内存（当前实现）。否决原因：大表 OOM，多步后更严重。
- **备选**：全部步骤落盘（类似外部排序引擎）。否决原因：小数据量任务性能显著劣化，磁盘 IO 成为常态成本。

### D6. 写入：按 `commit_size` 批量提交，失败不回滚已提交批次

写入按批 commit，主键 upsert 模式下重跑天然幂等；非 upsert（append）模式下重跑可能产生重复，运行结果中明示该语义。

- **备选**：单事务全量提交。否决原因：百万行级任务事务过大，失败代价高且锁表时间长。
- **备选**：逐行提交（当前实现）。否决原因：吞吐差，网络往返成为瓶颈。

### D7. 可观测：步级指标入元数据，样本快照落本地

新增 `run_steps` 表（`run_id`、`node_id`、`type`、`in_rows`、`out_rows`、`rejected_rows`、`elapsed_ms`、`status`、`error`）；失败步骤自动、任意步骤手动把样本（默认 1000 行）写到 `data/runs/{run_id}/{node_id}.jsonl`，按 `snapshot_keep` 保留份数清理。

- **备选**：每步落 staging 表。否决原因：需管理 DDL、清理与目标库污染，且与「不让中间态进数仓」的目标冲突。
- **备选**：只写运行日志。否决原因：无法在画布上给出节点徽标，也无法沉淀步级指标做趋势分析。

### D8. 前端画布：`@xyflow/react` 作内核，节点与连线自绘

仅引入画布内核（拖拽、缩放、连线、命中测试），节点渲染、连线样式、配色全部用现有设计 token 自绘，保持 macOS 视觉一致；后端为步骤类型的权威来源（`GET /api/pipeline/steps`），前端仅维护图标与分组的展示映射，并用一致性测试守门（类比既有 `EXPR_FUNCTIONS` 的做法）。

- **备选**：完全自研 SVG 画布。否决原因：拖拽/缩放/连线命中/视口裁剪的边界情况多，P1 至少多花一周且后续交互债高。
- **备选**：AntV X6 / G6。否决原因：能力溢出、包体大、样式侵入强，偏图编辑而非数据流编排。

### D9. 增量水位：平台侧持久化，成功后推进

水位存于任务运行状态（元数据库），执行前注入抽取条件，成功后推进到本次源端抽取行的最大值；无行或失败不推进。首跑按 `first_run_policy` 决定是否附加水位条件。

- **备选**：每次运行查询目标表 `MAX(watermark_field)`。否决原因：依赖目标可读与列存在，且目标被人工改动后水位语义漂移；多源合并时无法确定单一目标列。
- **备选**：沿用环境变量注入（当前实现）。否决原因：执行器从未设置，等价于未实现，且无法持久化。

### D10. 校验分两层：连线即时 + 保存全图

连线时只做能即时判定的规则（成环、源入边、目标出边、度数上限）；保存时做全图校验（含合并节点入边数、孤立节点、列可对齐性）。理由：即时反馈降低挫败感，全图校验保证被 API 直接提交的配置也合法（前端不是唯一入口）。

- **备选**：只在保存时校验。否决原因：用户在画布上得不到反馈，容易堆出一张坏图再被整体拒绝。

### D11. 步骤注册表由后端声明，带执行元数据

每个步骤类型注册：`type`、中文名、分类、入出边约束、是否 blocking、配置 schema、执行函数。前端节点面板与配置抽屉由该声明驱动，`/api/pipeline/steps` 暴露只读清单。

- **备选**：前端硬编码步骤清单。否决原因：会与后端实现漂移，且新增步骤需双端改；已有表达式函数清单的漂移风险先例。

## Risks / Trade-offs

- **升级后定时任务开始真实写入** → 属于行为修正，但对已有环境是「突然有写操作」。缓解：发布说明显著标注；升级后建议先在日常库验证；`Schedules` 页提供一键停用入口（已有）。
- **解释器性能低于内联脚本**（Python 逐行 + 节点调度开销）→ 缓解：分批 + 行级步骤批内零拷贝映射；`blocking` 步骤用排序/哈希聚合而非 O(n²)；P2 可评估可选执行后端。
- **历史脚本与新配置并存导致两套语义** → 缓解：`readers` / `writers` 契约冻结并加回归测试；解释器只接管含 `pipeline` 的配置；手写脚本路径行为不变。
- **画布状态复杂（选中、抽屉、连线、预览）易出交互 bug** → 缓解：状态收敛到单一 reducer，节点配置走受控组件；关键交互（连线拒绝、抽屉不丢配置、删除节点级联）列为验收项。
- **spill 文件占磁盘** → 缓解：`spill_threshold_mb` 与运行级配额，运行结束清理，异常退出由启动时清理残留目录兜底。
- **合并列对齐的静默错误** → 缓解：合并节点显式展示对齐结果与类型推导，缺失列与类型冲突标注为提示，不静默处理。
- **配置体积增大影响既有存储列长度** → 缓解：配置以 JSON 存 TEXT/JSON 列，MySQL 侧确认列类型；版本快照保留旧结构以便回滚。

## Migration Plan

1. **后端先行（不改行为）**：引入 pipeline 模型、步骤注册表、解释器与 `fields → pipeline` 编译；此时执行通道仍走旧脚本，跑全量回归确认存量任务行为不变。
2. **执行通道切换（单独提交，可回滚）**：调度改用真实执行通道、注入并推进水位、引入批次参数；该提交只依赖第 1 步的模型，回滚不影响配置数据。
3. **前端画布上线**：画布成为主要编排界面；旧的字段规则表单保留为画布内 transform 节点的「快速映射」视图（同一份配置的另一种编辑方式），避免用户失去熟悉入口。
4. **文档与默认值**：更新 `README`、`.env.example`（`batch_size` / `commit_size` / `spill_threshold_mb` / `snapshot_keep`）与步骤参考文档。
5. **回滚**：pipeline 配置对旧版本不可读，因此回滚需保留旧脚本产物（`scripts/current`）并在回滚前导出配置；同步在变更说明中标注该单向性。

## Open Questions

- `spill_threshold_mb` 与 `snapshot_keep` 的默认值（实现期按单机内存与磁盘实测确定，不影响规格与任务分解）。
- 步骤面板是否需要搜索与最近使用排序（可在 P1 实现后期根据可用性反馈决定）。
- 是否在后续变更中引入 `lookup`（静态码表已能覆盖大部分翻译场景，需真实用例驱动）。
