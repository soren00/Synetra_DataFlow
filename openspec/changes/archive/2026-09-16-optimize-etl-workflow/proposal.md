# Proposal: ETL 功能优化（连接双向 / 查询数据修正 / 任务表单增强 / 定时任务管理 / Postman 式 API 连接 / Kettle 对齐）

## Why

面向数据工程师的 Web 化 ETL 平台在易用性与能力完整性上存在六处短板，直接影响日常使用：

1. **源/目标强绑定连接方向**：连接创建时必须二选一（source/target），一个可一体读写的库无法既当源又当目标，新建任务时源/目标下拉互相不可见，使用受限。
2. **只读查询数据全显示为横线**：只读查询表格里所有单元格都是「—」，无法看到真实数据（定位为前端按列下标渲染缺失，详见 design）。
3. **新建任务表单体验差**：数据预览内嵌在模态框内不可关闭；字段转换规则与受限表达式对用户不透明（表达式含义不清、无参考）；抽取模式是单值下拉，增量/upsert 所需的多个字段无法充分表达；定时只能用 cron 原文输入，不够直观。
4. **没有定时任务管理**：任务只能填 cron 字符串，缺少统一的调度管理视图（列举、启停、下次运行时间、启停开关）；本地环境下定时从不真正触发。
5. **REST/API 连接不参照 Postman**：method、auth 等本可用下拉的字段全是自由文本输入，缺少 Query Params / Headers 结构化编辑，不符合数据工程师的调试习惯。
6. **整体未参照 Kettle**：缺少步骤级可见性、连接字段下拉化等易用性改进。

## What Changes

- **双向连接**：`ConnectionDirection` 新增 `both`（双方），连接管理可标记为「双方」，新建任务时源/目标下拉都能选择该连接。
- **查询结果修正**：只读查询页与任务预览的表格按「列下标」正确渲染真实数值，替代当前统一显示的「—」占位符。
- **任务表单增强**：
  - 数据预览抽为独立可关闭的弹窗；
  - 字段转换/受限表达式提供规则说明与可用函数参考，帮助用户理解各规则含义；
  - 抽取模式从单值下拉升级为按模式展开「多个组件字段」（增量字段/水位/首跑策略，upsert 主键多值等）；
  - 定时从 cron 文本框升级为「常用频率下拉 + 自定义 cron」。
- **定时任务管理**：新增调度管理视图，支持列出定时任务、启停开关、查看上次/下次运行时间；后端提供本地轮询/触发能力（LocalScheduler），使定时能真正发生。
- **Postman 式 API 连接**：HTTP 方法、认证方式改为下拉；支持 Query Params / Headers 结构化键值编辑。
- **Kettle 对齐（轻量）**：连接表单常用字段下拉化、任务运行增加明细日志入口；可视化步骤流水线、多源多目标编排不在本次范围（见 Open Questions）。

## Non-Goals（明确不做）

- 不做可视化「步骤流水线」DAG 编排（Kettle Spoon 式画布），不作为本变更范围。
- 不新增连接器类型（MySQL/PostgreSQL/Oracle/SQLServer/Hive/ClickHouse/CSV/API/对象存储维持现状）。
- 不改变既有任务配置/运行历史的数据结构兼容之外的行为。
- 不引入外部调度引擎；本地轮询调度（LocalScheduler）为定时触发的唯一实现。

## Assumptions

- 双向连接对存量连接保持兼容：已有 direction 维持不变，默认仍为 source。
- 查询行数据在 API 层保持「位置数组 `rows: list[list]`」的契约不变，修正仅在展示端完成，避免破坏下游消费方。
- 本地调度轮询器可配置启停（config 开关），为定时触发的唯一实现；验收以「本地开该开关后定时可真正触发」为准。

## Risks

- 本地轮询调度器作为后台进程的运行稳定性与生命周期管理（随主进程启停、异常恢复）。
- 抽取模式从单值改为多字段组件，需兼容既有已经保存的扁平 config（旧字段仍可解析）。
- 定时启停开关语义需要与既有 `schedule` 字符串字段共存，避免破坏任务列表展示逻辑。

## Open Questions

- **阻塞项**：Kettle 化是否必须在本变更排期？（见 Non-Goals，默认后置。）
- 定时管理入口是独立新页面，还是并入现有 ETL 任务页？（设计倾向于独立页，见 design.md 决策，可在 implement 时再定。）
