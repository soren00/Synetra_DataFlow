## Context

新建任务表单的「字段转换」区域用于逐条配置源字段→目标字段的转换规则。当前实现中，规则列表的标题行有两个按钮：「添加规则」（在末尾追加一条空规则）与「删除规则」（`setFields((fs) => fs.slice(0, -1))`，仅能删除最后一条规则，且列表为空时禁用）。

由于「删除规则」只能删末尾一条，用户无法删除中间的某条规则，必须先把末尾规则逐条删掉再重新添加，操作繁琐且容易误删无关规则。本变更把删除能力下沉到每条规则行内，替换为逐行「删除」按钮。

约束：`fields` 是前端本地状态数组，结构与后端保存链路（`fields[].source/target/kind/...`）无关；本次改动不触碰数据契约、后端与保存逻辑。

## Goals / Non-Goals

**Goals:**
- 允许用户删除字段转换列表中的任意一条规则，而非仅末尾一条。
- 删除操作只影响被点击的那条规则，其余规则内容不变。

**Non-Goals:**
- 不修改「添加规则」的交互与位置。
- 不改变 `fields` 的数据结构、保存链路与后端契约。
- 不引入拖拽排序、批量多选删除等能力。

## Decisions

1. **删除按钮放在每条规则行尾**：将「删除」按钮置于规则行的最末尾（在源字段、规则类型、目标字段以及 `cast_to`/`null_default`/`constant_value` 等条件输入之后），保证无论规则类型如何，删除按钮始终固定在行尾。
   - 备选：放在目标字段输入之后、条件输入之前 —— 被否决，因为类型转换/空值填充/常量规则会多出条件输入，删除按钮会被夹在中间，视觉顺序混乱且不统一。

2. **删除按索引过滤实现**：用 `setFields((fs) => fs.filter((_, j) => j !== i))` 删除用户看到的第 `i` 行，与现有 `setRule` 的下标语义一致。
   - 备选：按 `source` 字段名删除 —— 被否决，`source` 可能为空或重复，无法唯一定位目标行。

3. **按钮样式复用现有 `Button variant="ghost"`，文案为「删除」**：与「添加规则」「AI 生成」等行内 ghost 按钮视觉一致。
   - 备选：仅用 `IconButton` 的 trash 图标、无文字 —— 被否决，用户明确要求「删除」文字，纯图标可识别性弱、易误触。

4. **移除标题行的「删除规则」按钮，保留「添加规则」**：删除入口完全下沉到行内，标题行只保留新增能力。

## Risks / Trade-offs

- 规则行使用 `key={i}`（下标）：删除中间行会使后续行的 key 前移，可能引起这些行输入框的焦点丢失。由于所有输入均为受控组件、值保存在 `fields` 状态中，不存在数据丢失，焦点短暂丢失属可接受。
  → 缓解：本次不改 key 生成策略；如后续需要稳定焦点，可改用稳定标识作为 key（不在本次范围）。
- 删除与 AI 表达式弹窗的下标引用：AI 弹窗以 `ai.index` 引用 `fields[ai.index]`，若弹窗打开期间删除规则会导致下标漂移。正常流程中弹窗遮罩层会挡住规则列表，二者不会同时操作。
  → 缓解：不额外处理，属非阻塞边缘情况。

## Migration Plan

纯前端改动，无数据/后端迁移。部署后执行前端构建（`vite build`）并回归任务表单的字段转换交互即可，无需回滚预案。
