# Design: 多轮对话会话 + 表达式 Skill

## Context

当前 AI 生成链路的事实（均在探索阶段定位）：

| 事实 | 位置 |
|---|---|
| 表达式 = 受限 Python 表达式，`ast.parse(mode="eval")` + AST 白名单 + 清空内建的 `eval` | `services/backend/app/expr/whitelist.py:24-65` |
| 白名单为 16 个函数硬编码常量 | `whitelist.py:14-17` |
| 同一份白名单命名空间被**复制**进生成脚本源码字符串 | `app/scripting/gen_config.py:19-29,103-106` |
| 规则类型 = direct/constant/null_fill/cast/expression；表达式落在 `fields[].expression` | `app/models/task_config.py:21-38,58` |
| 保存链路校验入口 = `validate_rules`（违规 → 422） | `app/transform.py:62-73`、`api/tasks.py:73` |
| RAG 只加载 `app/llm/contracts/*.md`，目录内仅 `etl_sdk.md`（无表达式内容） | `app/llm/rag.py:11-19` |
| 自然语言建任务路径**不走 RAG**，第二轮提示的字段示例只有 `kind:"direct"` | `app/llm/task_draft.py:352-378` |
| **供应商接口每次只发 `[system?, user]` 两条 message，无 assistant 轮次** | `app/llm/deepseek.py:35-42` |
| **每轮把骨架/表结构/草稿 JSON 重新拼进新 prompt** | `app/llm/task_draft.py:143-162`、`324-389` |
| **会话历史仅存在于前端内存、仅用于展示，从不上送** | `src/pages/ConversationTask.jsx:20,45,62-69` |

结论：与大模型的对话**不是多轮**，是「无状态单轮调用 + 服务端人工拼接上下文 + 前端本地展示」；同时表达式规范在提示词与 RAG 中双双缺失，且权威清单已被复制成两份。

**实测补充（实现期用探针验证，影响技能包内容与反例口径）**：校验器的真实边界比"白名单函数"更细——

| 写法 | 静态校验 | 说明 |
|---|---|---|
| `lower(email)` / `concat(id,'-',name)` / `round(amount,2)` | 通过 | 推荐写法 |
| `a + '-' + b`、`a if a else b`、`a > 0`、`sum([a,b])` | 通过 | 纯操作符，未触碰 Attribute/Call，合法可用 |
| `f'{a}-{b}'`、`a % b` | 通过 | 能通过校验，但与 `concat()` 语义重复 → 技能包归类为「不合规范、应改用 concat」 |
| `.strip()` / `.format()` / `datetime.now()` | **拒绝** | 属性访问 / 非白名单调用 |
| `coalesce(...)` / `__import__(...)` / `eval(...)` | **拒绝** | 函数不在白名单 |
| `row['a']` | 通过（静态） | 运行期 `row` 未定义 → NameError；属"静态通过但运行期报错"类 |

因此技能包必须区分「被拒绝」「静态通过但运行期报错」「通过但不合规范」三类，而不是笼统地说"非白名单都会 422"。

## Goals / Non-Goals

**Goals:**

- 把 AI 生成 ETL 任务的对话改为**真多轮**：会话内维护模型可见轮次历史，修订/修复作为后续轮次追加。
- 沉淀一份**随服务分发、可审阅、可测试**的表达式技能包，讲清「各类表达式怎么用、什么时候不该用表达式」。
- 让「自然语言→TaskConfig」与「TaskConfig→Python 脚本」两条生成路径都拿到技能包，且在会话中只注入一次。
- 把「文档列出的函数」「校验器白名单」「生成脚本运行时函数」收敛为单一事实源，且漂移能被测试检出。
- 形成「讲清规范 → 生成 → 校验 → 修复」的闭环，并让违规对用户可见、不落库。

**Non-Goals:**

- 不在服务端持久化会话（不建会话表、不引入 `conversation_id` 生命周期）。
- 不做流式输出、不做工具调用/函数调用（接入层仍是单次请求-响应）。
- 不扩展表达式能力本身（不新增函数、不放开属性访问）——本次只解决"用对"。
- 不做对外表达式参考 API 或前端「表达式参考」面板。
- 不改手写 Python 路径（不受白名单约束，安全模型独立）。
- 不改 `TaskConfig` 契约与运行语义。

## Decisions

### 决策 1：多轮会话采用「服务端编排 + opaque 历史回传」的无状态多轮

**决策**：服务端在每次响应中返回 `history`（本轮之后、模型可见的完整轮次数组，元素为 `{role, content}`）；客户端 opaque 保存并在下一次请求中回传；服务端不保存会话状态、不引入会话存储。`system` 段落每轮由服务端重新组装（含表达式技能包），**不接受客户端提供的 system**。服务端对回传 `history` 做结构校验（`role ∈ {system,user,assistant}`、必填 `content`、单条与总字符上限、轮次顺序）与超限裁剪。

**理由**：用一个纯函数的请求-响应契约就拿到"真多轮"的全部收益（模型看到自己的前序输出、修订轮不缺上下文），同时避开会话存储带来的生命周期、并发写入、清理策略与"他人能否读该会话"的权限问题；与既有 REST 风格和 `/draft`、`/revise` 两个既有入口兼容。

**被否决的方案**：

- **服务端持久化会话（`conversation` 表 + `conversation_id`）**。否决理由：需要新增会话生命周期、并发写入、过期清理与访问控制，而本变更目标是生成质量；审计事件已能覆盖"一次多轮会话可回溯"的需求，留档收益不抵复杂度。
- **维持现状（历史只在前端展示、不上送）**。否决理由：这正是本次要修的缺陷。
- **把历史压缩成一段 summary 文本每轮重发**。否决理由：丢掉轮次角色结构，模型依旧看不到自己的输出，等于换皮单轮，且 summary 会损失字段名等需要精确的信息。

### 决策 2：会话轮次编排——内部编排轮次同样入会话

**决策**：骨架识别轮、源表结构注入轮、完整草稿轮、修订轮、修复轮都成为会话中的轮次。源表结构以 `user` 角色消息（带「已识别骨架」「源表结构（来源：…）」标签）追加进历史；assistant 的 JSON 输出原样入历史。草稿 JSON 不再在修订轮重复拼接。

**理由**：模型能看到自己的前序输出后，「保持字段映射稳定」由历史自然保证；技能包与表结构只出现一次，轮次增长只带来历史本身的体积增长，而不是"每轮都重发全部上下文"的乘法增长。

**被否决的方案**：只把「用户 ↔ 助手」视为会话轮次、内部编排（骨架/表结构）继续藏在 prompt 里。否决理由：模型仍看不到骨架识别结论，修订轮依旧缺关键上下文，问题只解决一半。

### 决策 3：历史长度与成本控制——硬上限 + 从最早非 system 轮次裁剪

**决策**：单会话历史按「最多 N 轮（默认 20）」与「总字符上限（默认 60K）」双限裁剪，裁剪从最早的非 `system` 轮次开始，`system`（含契约与技能包）永不被裁剪；发生裁剪时响应带 `history_trimmed: true` 提示，并把裁剪事实写入审计。

**理由**：多轮必然带来历史增长，无上限会让成本、延迟与失败率失控；表达式技能包属于会话级上下文，被裁剪会直接破坏本次变更的核心价值，因此必须保护。

**被否决的方案**：

- **不裁剪**。否决理由：长会话必然超出上下文窗口，表现为供应商 400 或输出质量骤降。
- **用 LLM 摘要压缩历史**。否决理由：引入额外调用与不确定性，且摘要易丢失字段名、表名这类必须精确的信息。
- **按字符数等比截断内容**。否决理由：会截断 JSON 结构导致历史不可解析，破坏后续轮次。

### 决策 4：接入层 API 形态——`converse(messages) ` 为一等抽象，`complete` 为薄封装

**决策**：`LLMProvider` 的抽象方法改为 `converse(messages: list[Message], *, system: str | None = None) -> str`；保留非抽象的 `complete(prompt: str, *, system: str | None = None) -> str`，内部构造单条 `user` 消息调用 `converse`。`DeepSeekProvider` 直接把消息列表映射为 payload 的 `messages`。既有脚本生成路径与 `FakeProvider` / `RecordingProvider` 只需实现 `converse`，单轮调用点无需改动。

**理由**：多轮应是接入层的一等能力（否则供应商实现会永远绕开它）；同时脚本生成路径是单轮语义，保留 `complete` 可把改动面压到最小。

**被否决的方案**：

- **新增 `chat(messages)` 并让 `complete` 同为抽象方法**。否决理由：两条抽象方法会让每个供应商实现出现"两条路径各写一遍"的分裂，而 `complete` 实际永远是特例却占据抽象地位。
- **把 `complete` 的 prompt 类型放宽为 `str | list[dict]`**。否决理由：联合类型让调用点可读性变差，且既有实现会静默按字符串处理。
- **让调用方自行拼装 payload**。否决理由：泄露供应商细节，破坏"切换供应商不改变既有行为"的既有承诺。

### 决策 5：技能包形态——独立 skill 包目录，而不是塞进 `contracts/` 或提示词常量

**决策**：在 `services/backend/app/llm/skills/expression/` 下放技能包：`SKILL.md`（规范主体，带 YAML frontmatter `name` / `description` / `applies_to`）与 `examples.md`（正反例对照 + 常见需求配方）。目录布局与仓库既有 `.codebuddy/skills/<name>/SKILL.md` 约定同构，便于后续按能力粒度扩充。

**理由**：技能是「按能力粒度选择注入」的单元，与 `contracts/`（SDK 契约冻结点的整体注入）语义不同；独立目录让注入范围可控、内容可审阅、可被测试逐节断言。

**内容契约补充（实测反馈驱动，见 tasks §7）**：技能包只覆盖「有哪些函数」是不够的——实测中用户提出掩码需求（「姓名的第二个字转换为*，手机号中间四位转换为*」），模型因技能包未讲「取子串靠切片」而回落到 SQL 方言 `CONCAT(LEFT(...),'*',SUBSTRING(...))`，被 422 拒绝。因此技能包的内容契约必须额外覆盖：
1. **可用的操作符与切片**（`col[0]`、`col[a:b]`、`col[-n:]`、`+` 拼接、比较、三元）——取子串的唯一手段；
2. **SQL/数据库习惯 → 合规等价写法对照表**（`CONCAT`/`LEFT`/`RIGHT`/`SUBSTRING`/`COALESCE`/`CASE WHEN`/`CAST AS`/`TRIM`/`LENGTH`），并强调函数名**大小写敏感**；
3. **常见业务配方**（拼接、去空格、大小写、四舍五入、类型转换、空值兜底、**脱敏/掩码**），以及**无法表达**的需求须如实标注（如邮箱按下标打码，因无 `index`/`find`/`split`）。

**被否决的方案**：

- 直接写进 `app/llm/contracts/etl_sdk.md`。否决理由：混入使用规范会模糊"契约 vs 指南"的边界。
- 把规范硬编码进 `task_draft.py` 的提示词常量。否决理由：不可独立审阅、无法与白名单做一致性测试。
- **把 `left`/`right`/`substr` 加进白名单函数**（让 SQL 习惯写法直接可用）。否决理由：属于扩展表达式能力，超出本变更 Non-Goals；切片已能完整表达取子串语义，加函数会引入与 `cast`/`len` 的语义重叠与新的边界问题（如越界、负索引），且会固化"函数式 SQL 方言"的写法。
- **校验时对函数名做大小写不敏感匹配**（让 `CONCAT` 生效）。否决理由：会放宽校验语义、改变既有失败/成功边界（`apply_expression` 的命名空间键是小写），属于能力扩展；改用"技能包明确 + 修复提示明确"来消除该误写，实测已能一次写对。

### 决策 6：单一事实源——清单由代码导出，文档由测试守住

**决策**：

1. `app/expr/whitelist.py` 增加权威访问器 `allowed_functions()` 与 `forbidden_notes()`，并导出供生成脚本复用的命名空间源码常量 `EXPR_NS_SOURCE`（**校验与求值行为一字不改**）。
2. `app/scripting/gen_config.py` 的 `_EXPR_NS_SRC` 不再内联维护函数清单，改为由 `EXPR_NS_SOURCE` 渲染，消除第二份副本。
3. 技能包的「受支持函数」表格与「禁止项」清单由一致性测试守门：解析 `SKILL.md` 中声明的函数集合并与 `allowed_functions()` 比对，不等即失败。

**理由**：代码是行为真相，文档必须跟着代码走；用测试而非人工约定来保证，是唯一能长期不漂移的做法。

**被否决的方案**：

- **纯手写文档 + 人工维护**。否决理由：`gen_config.py` 已经发生过一次复制，说明人工同步不可靠。
- **运行时把函数清单动态渲染进 prompt**。否决理由：签名语义、边界、正反例、配方这类自然语言说明无法从代码渲染，动态拼装只能覆盖清单，反而制造两套来源。故采取"手写说明 + 清单由测试守门"的折中。

### 决策 7：注入机制——RAG 扩目录 + 会话级 system 一次注入

**决策**：

1. `app/llm/rag.py`：加载范围由「`contracts/*.md`」扩展为「`contracts/*.md` + `skills/*/SKILL.md`」（按目录名排序、拼接带技能名小标题），`build_rag_context()` 签名与"供应商无关"语义不变，从而**自动覆盖** `ScriptGenerator` 脚本生成路径。
2. `app/llm/task_draft.py`：表达式技能包作为**会话级 `system` 段落**注入一次（与既有的"只输出 JSON、不得虚构连接"系统提示合成同一段落），轮次历史中不再重复出现；骨架轮同样携带该 `system`（保证第一轮就受规范约束）。
3. 审计事件记录本次注入的技能名与指纹（如 `skills: ["expression@<sha8>"]`），使"某次生成用了哪版规范"可回溯。

**理由**：多轮会话下，把技能包放进每轮 user 消息会造成线性重复、浪费上下文并可能被历史裁剪；放进 `system` 既只出现一次，又因服务端每轮重建而不会被客户端篡改。

**被否决的方案**：

- 每轮把技能包追加进 user 消息。否决理由：重复膨胀、且会被历史裁剪策略影响。
- 把技能包放进前端回传的历史里。否决理由：客户端可伪造，破坏"规范不可篡改"。
- 让 LLM 通过工具按需读取技能文件。否决理由：接入层无工具调用能力。

### 决策 8：规则类型选择引导——给判据，不给禁令

**决策**：生成提示与技能包中给出五类规则的选择判据（能映射→`direct`；固定值→`constant`；空值兜底→`null_fill`；纯类型转换→`cast`；以上都不行才→`expression`），并把 `fields` 示例从单一 `kind:"direct"` 扩展为覆盖 `cast` / `null_fill` / `expression` 的示例组。

**理由**：表达式风险面最大（可被 AST 拒绝、语义易错），而生成本可被更简单、可被确定执行的 kind 覆盖。

**被否决的方案**：不引导、放任 LLM 自由选择 kind。否决理由：现行提示只给了 `direct` 一种示例，LLM 在需要转换时会自行发明 `expression`，正是当前误写的主要来源。

### 决策 9：校验回环——复用保存链路的同一个校验器，修复作为会话后续轮次且限一次

**决策**：

1. **校验器复用**：生成侧与保存侧共用 `app/transform.py:validate_rules` / `app/expr/whitelist.py:validate_expression`。
2. **草稿路径回环**：完整草稿轮与修订轮产出后立即校验 `fields`；若违规，把「违规字段 + 违规原因 + 规范要点摘要」作为**同一会话的下一轮 user 消息**追加，调用同 provider 生成修复稿；**修复最多 1 次**（与 `_round` 的"输出非法重试"是两层，独立计数），审计 `round="repair"`。仍违规则保留草稿并写入字段级告警。
   - **修复提示必须给「怎么写」而不只是「有什么函数」**（实测反馈，见 tasks §7）：提示中的写法要点改由技能包的 `WRITING_TIPS` 标记块派生（`rag.skill_block("expression", "WRITING_TIPS")`），与禁止项（`forbidden_notes()`）、可用函数（`allowed_functions()`）一并注入。早期只列函数清单的提示无法修复"掩码"类违规（模型无函数可用，只能继续写 SQL 方言），修复轮最终把字段降级为 `direct` 静默丢功能。
3. **脚本路径**：`ScriptGenerator.generate` 前置对任务配置跑 `validate_rules`（配置层表达式必须合规，否则拒绝生成并给出可读原因）；技能包明确要求「脚本从 `fields[].expression` 读取表达式，不得自行硬编码表达式逻辑」，从而让脚本内联表达式的合规性由配置层校验唯一覆盖。
4. **违规不落库**：沿用既有保存链路 422 语义。

**理由**：回环的价值在于"用确定性的校验器补 LLM 的随机性"；在多轮会话下修复轮天然复用历史，无需重发草稿；限一次是为了不让一次生成触发不可控的调用次数与费用。

**被否决的方案**：

- **无界重试直到合规**。否决理由：成本与延迟不可控，且白名单外需求（如需要 `datetime`）无论重试多少次都无法满足。
- **只告警不重试**。否决理由：把修复成本转移给用户，与"提升准确性"目标相悖。
- **为修复轮单独开一次无状态调用（不回传历史）**。否决理由：模型看不到自己刚写错的内容，修复效果与效率都更差。
- **对生成脚本做表达式字面量 AST 反抽取再校验**。否决理由：生成脚本形态不受控，反抽取脆弱易误判；改用"配置层校验 + 技能约束脚本只读配置"更稳。

### 决策 10：违规可见性——结构化告警字段，不动对外参考接口

**决策**：草稿响应在既有 `warnings` 之外新增结构化字段 `expression_issues: [{"field","target","message"}]`（纯新增，向后兼容）；前端 `ConversationTask.jsx` 在草稿卡按字段标注，`Tasks.jsx` 在表达式输入处展示后端返回的违规原因。**不新增** `/api/expr/reference` 之类对外接口。

**理由**：既满足"违规可见"，又不引入技能包的第二套消费契约。

**被否决的方案**：新增参考 API 驱动前端参考面板。否决理由：本次范围外，且会与技能包形成两份需同步的对外契约。

**补充（实测反馈，见 tasks §7.6）**：不新增对外接口 ≠ 允许前端文案脱离权威口径。实测发现 `Tasks.jsx` 的 `EXPR_HELP` 手写文案出现两处偏差——把引用对象写成「**目标**列名」（实现只支持**源**列名，属事实错误），且未讲切片（用户在表单里同样写不出脱敏表达式）。因此采纳「保留内联文案 + **跨端一致性测试守门**」：文案的 `EXPR_FUNCTIONS` 列表与示例表达式由 `tests/test_frontend_expr_help.py` 与 `allowed_functions()`/`validate_expression` 逐项比对，并断言不得出现「目标列名」。这样既守住 Non-Goal（不加接口），又让前端成为同一权威口径的被校验消费方。

## Risks / Trade-offs

- [客户端篡改或污染历史] → 服务端校验 `history` 结构与长度、`system` 段落每轮由服务端重建、生成结果仍需人工确认与表达式校验；不做 HMAC 签名（结构校验 + 保存链路校验已覆盖风险，签名收益有限）。
- [历史回传使请求体变大] → 双限裁剪（轮次 + 字符）+ 只回传"模型可见轮次"（不含前端展示用的本地提示消息）。
- [既有 `FakeProvider` / `RecordingProvider` 需适配多轮签名] → 抽象方法只增加 `converse`，`complete` 保留为薄封装，测试替身只需实现一个方法。
- [多轮放大 token 成本] → 会话级上下文只注入一次；历史双限裁剪；审计按会话记录轮次便于观察成本。
- [技能文档与代码漂移] → 清单由代码导出 + 一致性测试守门（决策 6）。
- [过度引导压制 LLM 判断] → 判据以"优先简单 kind"表述，非硬性禁止；技能包同时说明何时确实应当使用表达式。
- [技能包被当成 SDK 契约误改] → frontmatter 标注 `applies_to: field-rule-expression`，注入时带技能名小标题与 `contracts/` 段落区分。
- [多轮改动触及面广（接入层 + 编排 + API + 前端）] → 保留 `complete` 与"不传 `history` 时退化为既有单轮编排"两条兼容路径，可分步落地、逐步切换。

## Migration Plan

- 分步落地：①接入层加 `converse`/保留 `complete` → ②会话编排与 `history` 契约 → ③技能包与单一事实源 → ④注入与校验回环 → ⑤前端回传与告警展示。
- 兼容性：请求不带 `history` 时，`/llm/tasks/draft` 与 `/draft/revise` 退化为既有单轮编排（行为与字段不变）；`TaskConfig` 契约、手写 Python 路径、保存链路 422 语义均不变；无 **BREAKING**。
- 部署：随代码发布即可生效；无数据库迁移、无配置项变更（新增上限阈值有默认值）、无外部依赖。
- 回滚：删除 `skills/` 目录、回退注入/回环调用、忽略 `history` 字段即可恢复原行为；`history` 与 `expression_issues` 均为新增可选字段。
