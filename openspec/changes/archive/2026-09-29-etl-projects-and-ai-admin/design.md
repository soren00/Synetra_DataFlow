# Design: ETL 项目分组与 AI 资产管理

## Context

现状（已核实）：

- `project` 只是散落在 `connection`/`task`/`run_record`/`service_credential`/`trigger_log` 等表上的自由文本列，没有任何项目实体、清单或 CRUD API；前端 `Tasks.jsx` 与 `Connections.jsx` 各自硬编码 `"demo"`，新建任务表单中没有项目输入框，`ConversationTask.jsx` 甚至是从连接表反推项目清单。
- 新建任务表单的字段规则行把「源字段 / 规则类型 / 目标字段 / 表达式」挤在同一行，表达式提示 `EXPR_HELP` 紧贴其下；提示文案受 `tests/test_frontend_expr_help.py` 守门（函数清单必须与后端白名单逐字一致，且必须包含源列名/切片/小写与 9 个 SQL 方言词）。
- 表达式白名单（`app/expr/whitelist.py`）、表达式技能包（`app/llm/skills/expression/`）、多轮会话与修复回环（`app/llm/task_draft.py`）已就位，技能包内容每次生成请求实时读盘。
- AI 生成路径**不落库**：`task_draft.py` 明确「草稿不落库」，审计事件 `llm_draft_call` 只记录供应商/模型/轮次/成败/会话标识/技能指纹，**不含提示词原文**；`examples.md` 实际上并未被 `rag.py` 加载（只 glob `*/SKILL.md`）。
- 前端无路由库，侧边栏由 `App.jsx` 的 `NAV` 数组驱动；UI 组件库已有 `Pager`（服务端分页受控组件），`Overview.jsx` 已示范「分页与筛选全部交由后端裁决」的写法。

## Goals / Non-Goals

**Goals:**

- 让 ETL 任务具备「先项目、再任务」的组织能力，并把项目归属从自由文本收敛为显式实体。
- 让表达式输入获得独立空间，同时不削弱既有提示口径与一致性守门。
- 让单条字段规则可以按提示词生成表达式，且生成结果仍由白名单与保存链路守门。
- 让 AI 生成 → 确认创建的全过程可复盘：每次创建留一条含提示词链的记录，并可分页筛选浏览。
- 让技能包成为可运维资产：可查看、可编辑，且保存前受一致性校验保护。

**Non-Goals:**

- 不把连接、调度、血缘、主数据纳入项目归属（连接保持全局可用）。
- 不改写或精简表达式提示文案（本次仅调整排版）。
- 不新增/删除技能包，不支持技能包目录结构变更。
- 不引入前端路由库或新的分页范式。
- 不改变 `POST /llm/tasks/draft` 系列的响应结构。

## Decisions

### 决策 1：项目为真实实体（表 + 最小 CRUD），而非派生视图

**决策**：新增项目表与项目清单 API，支持创建、列出、查看概要、删除；`TaskConfig.project` 继续作为归属字段，值由导航上下文注入。

**理由**：需求形态是「先建项目 → 点进去 → 再新建任务」，这要求**尚无任务的项目也能存在**——派生视图（从 `distinct task.project` 拼列表）无法表达空项目，直接使流程不成立。同时真实实体才能承载删除约束与任务计数。

**被否决的方案**：从既有 `task.project` 派生项目清单。否决理由：无法表示空项目，用户必须「先建任务」才能看到项目，与目标流程相反；且无法管理删除。

### 决策 2：项目只归属任务，连接保持全局

**决策**：项目详情内新建任务时，数据源/数据目标下拉展示**全部可用连接**，不按连接自身的 `project` 过滤；`connection.project` 退化为不再参与任何过滤的历史字段。

**理由**：既然项目不管理连接，按 `conn.project` 过滤只会产生「连接存在却选不到」的困惑，且会让既有连接（多为 `demo`）在新项目下集体不可用。全局可用与「项目管理只管任务」的边界自洽。

**被否决的方案**：按 `conn.project == 当前项目` 过滤连接。否决理由：与范围声明矛盾，且制造可见性陷阱。**被否决的方案**：把连接一并纳入项目管理。否决理由：显式超出本次范围，改动面扩散到连接 CRUD、凭据与外部触发。

### 决策 3：存量归属以「幂等播种」承接

**决策**：项目清单首次被请求时，若项目表为空，则把 `distinct task.project`（空值归入默认项目）播种为项目条目；播种幂等，重复启动不产生重复项。

**理由**：既有任务必须继续可见可进入，否则引入项目实体即等于「任务消失」。播种而非强制迁移，避免写迁移脚本与停机窗口。

**被否决的方案**：编写一次性数据迁移。否决理由：SQLite 幂等建表已是既有做法，播种逻辑更易测试与回滚。**被否决的方案**：不播种，只对新建任务生效。否决理由：既有任务从清单中消失，用户直接感知为数据丢失。

### 决策 4：两级导航用页内视图状态实现

**决策**：项目清单与项目详情作为两个页内视图（`项目列表 ⇄ 项目内任务`），通过组件状态切换并「返回」；不引入前端路由库，不改动侧边栏的顶级项语义。

**理由**：`App.jsx` 是数组驱动的无路由导航，引入路由库的收益不足以覆盖改造面；「点进去 / 返回」正是页内视图的自然语义。

**被否决的方案**：引入 `react-router`。否决理由：需要重写导航与全部页面挂载方式，与本次目标无关。**被否决的方案**：把项目清单做成独立顶级 NAV 项，任务页仍在导航中。否决理由：「点进去再是新建任务」的层级关系无法表达，且会出现两个入口指向同一批任务。

### 决策 5：表达式只调排版，不动提示文案

**决策**：规则行拆为两行——上行「源字段 / 规则类型 / 目标字段（及类型/填充值/常量值）」，下行「表达式输入 + AI 生成按钮 + 提示块」；`EXPR_HELP` 与 `EXPR_FUNCTIONS` 文案与声明形态保持不变。

**理由**：`tests/test_frontend_expr_help.py` 通过正则从源码中提取 `EXPR_HELP` 与函数清单并核对口径（含 9 个 SQL 方言词与 ≥4 个可求值示例）。保持文案与声明形态不动，即是零风险地获得布局改善。

**被否决的方案**：精简提示文案并同步修改守门测试。否决理由：本次明确只做换行排版；改动守门口径属于独立的文档变更，应单独评估。

### 决策 6：表达式 AI 生成走服务端新端点，复用既有校验与修复回环

**决策**：新增表达式生成端点，请求携带提示词、源字段、目标字段与源列清单；服务端复用 `expression` 技能包的 `WRITING_TIPS` 标记块作为规范上下文，输出候选后跑 `validate_expression`，失败时追加**一次**修复轮；结果仅回填，不自动保存。上下文中**不包含样例数据行**。

**理由**：白名单校验、技能包注入、修复回环三者都已在服务端就绪，放在服务端可以得到与草稿生成一致的口径、审计与脱敏保证。

**被否决的方案**：前端直接拼提示词调用模型。否决理由：绕过服务端脱敏与审计，且需在前端复制规范口径。**被否决的方案**：把源表样例数据行一并作为上下文。否决理由：样例含真实数据，扩大数据出平台面；列名足以支撑表达式生成。

### 决策 7：创建记录与任务落库同路径完成

**决策**：在任务保存请求上新增**可选**的 AI 提示词链字段；保存处理中先执行校验，若校验失败则写入一条失败记录后抛出原错误，若成功则落库并写入成功记录。提示词链由前端维护并随创建请求回传。

**理由**：单一路径可保证「任务存了但记录没写」「创建失败却漏记」两类裂缝都不出现，且不复制保存链路中的校验、血缘入库与脚本自动生成三段逻辑。

**被否决的方案**：新增独立的 `POST /llm/tasks/confirm` 包装端点。否决理由：需复制保存链路三段逻辑，长期维护双份。**被否决的方案**：前端创建成功/失败后再单独提交记录。否决理由：失败场景依赖前端二次请求，网络异常即漏记；且两次写入之间无一致性约束。

### 决策 8：记录持久化与分页契约对齐既有运行历史

**决策**：新增生成记录表（操作者、项目、状态、提示词链、草稿快照、失败原因、任务标识、模型与技能指纹、会话标识、时间）；查询接口采用与 `GET /runs` 相同的 `page/page_size/status` 契约（后端回夹页码、返回总数与状态计数）；前端复用 `Pager` 组件。

**理由**：`Overview.jsx` 已经建立了「分页与筛选全部交由后端裁决」的成熟范式，照抄契约可将新页面的实现与心智成本降到最低，也避免出现第二套分页语义。

**被否决的方案**：为记录页新造一套分页参数与响应结构。否决理由：无收益，增加前后端不一致风险。**被否决的方案**：一次性返回全部记录、前端分页。否决理由：记录随使用持续增长，前端分页不可控。

### 决策 9：记录页作为 AI ETL 页的子视图

**决策**：在 AI ETL 任务页内以视图状态区分「对话」与「记录」两个视图，对话视图提供进入记录页的按钮，记录视图提供返回按钮。

**理由**：需求明确要求「跳转过去、并且能返回」。独立 NAV 项没有「返回」语义，页内子视图才是自然映射，且不改动侧边栏。

**被否决的方案**：把记录页做成独立顶级 NAV 项。否决理由：无法满足返回 AI ETL 页的要求，且与「记录属于该流程」的组织关系不符。

### 决策 10：AI 管理并入既有模型配置页，权限沿用管理员

**决策**：在现有的管理员专属「模型配置」页中以分页签（Tab）形式加入技能包管理，页面统称「AI 管理」；查看与编辑均要求管理员角色。

**理由**：模型配置与技能包管理同属「AI 相关资产」，合并可避免两个都叫「AI ××」的顶级入口互相割裂；`access-control` 已有「LLM 配置管理员专属」的既有约束，权限语义直接沿用，无需新造。

**被否决的方案**：新建顶级「AI 管理」NAV 项。否决理由：与模型配置职责重叠，用户需要记住两个入口；且需要额外定义权限与页面骨架。

### 决策 11：技能包可编辑，但以「保存即校验」保护一致性

**决策**：把 `tests/test_expression_skill.py` 中的结构与语义断言抽取为可复用的校验模块，**同一份校验**同时被测试与「保存技能包」接口调用；保存前校验不通过则拒绝写盘（返回可读原因），通过则原子写入并对后续生成即时生效，同时写审计记录变更前后指纹。

**理由**：技能包是决定生成质量的核心资产，而其正确性目前只由 CI 守门——在线编辑可以轻易破坏一致性，而运行时不会报错，只会静默劣化生成质量。把「文档即测试」前移为「保存即校验」，使可编辑性与安全不再二选一。原子写入（临时文件 + 替换）避免并发下读到半写内容。

**被否决的方案**：允许直接写盘、不做保存前校验。否决理由：一致性破坏只能被 CI 发现，生产上表现为生成质量静默下降，难以定位。**被否决的方案**：技能包只读展示。否决理由：不满足「可编辑」的需求。

### 决策 12：技能包编辑范围限定为既有技能包的既定文件

**决策**：仅允许编辑既有技能包目录下的既定文件（技能主文件与随包示例文件），技能包名称限定受限字符集，写入路径限定在分发目录内，不支持新建/删除技能包。

**理由**：编辑能力已覆盖运维诉求；开放目录结构变更会把「技能包」变成用户可自由扩展的体系，牵涉加载顺序、指纹、契约校验与部署一致性，超出本次范围。

**被否决的方案**：支持在界面上新建与删除技能包。否决理由：范围扩张且需要新的目录契约与冲突规则，本次不需要。

## Risks / Trade-offs

- [项目归属会改变任务保存载荷的解释方式] → 归属由导航上下文注入，表单不提供自由输入；实现后回归「任务在两个项目间的可见性」与既有任务编辑流程。
- [播种时机的竞态与重复] → 播种在项目清单请求路径上做「表为空才播种」判断，配合唯一约束，重复调用幂等。
- [生成记录持续增长] → 采用服务端分页与索引（时间、状态），保留策略作为非阻塞开放问题，不影响规格与任务分解。
- [技能包在线的保存前校验必须与 CI 守门同源，否则出现两套口径] → 抽出单一校验模块，测试改为调用该模块，禁止在测试中另写一份断言。
- [技能包写入与生成请求并发] → 原子写（临时文件 + 替换），避免生成请求读到半写文件。
- [提示词与草稿快照落库引入敏感内容] → 记录沿用既有脱敏口径，明确禁止明文凭证；样例数据行不进入记录。
- [非空项目不可删除可能让用户觉得受限] → 拒绝时给出明确原因与处理指引（先清空或迁移任务）。

## Migration Plan

1. 幂等建表：项目表与生成记录表随既有建表流程创建，不改变既有列。
2. 归属播种：项目清单首次请求时若项目表为空，则从既有任务的 `project` 值（空值归入默认项目）播种。
3. 前端切换：导航入口改为项目清单，任务页接收项目上下文；连接下拉不做过滤。
4. 记录与技能包接口为纯新增，不改变既有契约；任务保存请求的新字段为可选，旧调用方无需改动。
5. 回滚：`TaskConfig.project` 契约未变，前端可退回扁平任务列表；新增表与新增接口可闲置，不影响既有任务运行。

## Open Questions

- 生成记录的保留策略（是否设数量上限/定期清理、是否需要导出）——不影响规格与任务分解。
- `examples.md` 目前未被生成上下文加载（仅加载技能主文件）：本次只将其纳入查看、编辑与保存前校验；是否并入生成上下文留待后续增强。
- 项目是否需要重命名与描述编辑（本次提供创建、列出、查看概要、删除）。
